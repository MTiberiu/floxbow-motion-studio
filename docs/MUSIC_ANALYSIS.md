# Music Analysis

Music Analysis is a project workspace for inspecting one registered MP3 or WAV without requiring subtitles. It has one **Analyze Music** action and one current report. Lyrics Sync remains an independent project artifact and is never read or changed by this analysis.

## Data contract

The current report is `projects/<project-id>/music-analysis.json`, validated by `scripts/music-analysis-report.ts`. Version 3 adds the audio-only `vocalProfile` alongside version 2's stem-derived `musicalEvents`; versions 1 and 2 remain readable. It links to the stable Media Registry `assetId`, records the source display name, SHA-256, size and modification time, and stores analysis time and duration. `status` is `complete` only when structure, DSP and all four stem event passes are available; otherwise it is `partial`.

`structure` preserves the engine's BPM, beat timestamps, downbeats, beat positions and original section labels with their start/end times. If the structure engine is unavailable, BPM is `null` and all structure arrays stay empty. `dsp` stores up to 2,000 waveform peak buckets, half-second RMS energy values, detected onset accents, sample rate and channel count. `musicalEvents.events` stores time-coded stem onsets, vocal activity boundaries/pauses, strong mix impacts, measured energy rises and section boundaries. Every item retains its source and method; intensity is normalized onset strength where supplied, and no confidence score is added without a calibrated model. `musicalEvents.groups` groups two to four nearby drum, bass or other attacks with stable event IDs. Drum sublabels ending in `_like` are conservative frequency-band heuristics; `drum_hit` and all `other_transient` events remain unclassified. `vocalProfile` stores Demucs-Infer `vocals.wav` RMS at 50 ms with an activity mask, plus experimental librosa pYIN F0 at about 50 ms. It records Demucs-Infer/librosa versions and the analysis method. F0 samples include a validity mask, pYIN voiced probability and a flag for isolated octave outliers rejected when neighboring frames agree; ambiguous pitch remains null rather than being octave-corrected. These are audio-only series independent of subtitle timing. `provenance` reports engine status/version/device and the reason any part is unavailable. Optional `performance` records worker wall time and peak working set when the host exposes it.

The report is written with an atomic project-local save after the worker finishes. A later analysis replaces the current report. Audio remains a linked registry asset and is not copied. The source path stays in the host process; the renderer sees a stable asset ID and same-origin stream URL.

## Runtime and API

The live development shell exposes a **Music Analysis** workspace. It lists ready registered audio assets, starts one background job per project, polls progress, supports cancellation and reloads the saved report after completion. Job endpoints live under `/api/media/<project-id>/music-analysis`; the host accepts only a registered audio `assetId`, resolves it through the media store and launches `scripts/music-analysis-worker.py`. Arbitrary file paths are never accepted from the UI. Reports can be reopened through the GET route after restarting the app.

The optional Python runtime is kept in ignored `.studio/music-analysis-runtime`; model and package caches and reusable Demucs stems live in ignored `.studio/music-analysis-cache`. The source SHA-256 selects the stem cache. AIOI runs with `keep_byproducts=True`; its four stems are read for event DSP in that same worker. On a repeat analysis of the unchanged audio, AIOI receives `skip_separation=True` and reuses those cached files. The model spectrogram intermediates are removed after inference. None of these Python packages is an Electron dependency or project asset. The live analysis API is not currently packaged in the built snapshot. A production Electron distribution still needs a supported runtime bootstrap/packaging decision and an installation UX; do not claim that built apps can analyze yet.

## Engines and limits

The preferred structure engine is All-In-One-Infer 3.1.0 (`allin1_infer`), which supplies structure fields from its Harmonix model and uses Demucs separation. First inference downloads pretrained checkpoints from their upstream host; progress messaging distinguishes that first run from ongoing audio processing. Existing compatible stems can be supplied to the library API, but this v1 FloxBow UI does not yet discover or reuse project stems.

The DSP pass uses SoundFile for decoding and librosa for onset accents, stem-specific spectral flux, vocal stem activity windows and low/mid/high drum attack features. RMS energy and waveform peaks are computed directly from the decoded mix. If AIOI cannot create stems, the report remains partial and reports unavailable stem event analysis; it does not substitute guessed BPM, beat grid, sections or instrument identities. “Kick-like”, “snare-like” and “hi-hat-like” are transparent DSP heuristics, not a trained or calibrated classifier. This first event slice does not name instruments in the `other` stem.

FloxBow is an open-source application and does not bundle this Python runtime or downloaded model weights. Upstream code and model files keep their own licenses: All-In-One-Infer and the original Harmonix model declare MIT; Demucs-Infer declares MIT; Madmom-Infer code declares BSD-2-Clause, while its separately downloaded pretrained weights declare CC BY-NC-SA 4.0. Users who install and run these components are responsible for following the applicable package and model terms. The isolated environment includes PyTorch, librosa, SciPy and supporting packages; MP3 decoding depends on FFmpeg/ffprobe being available to the worker. See the experiment notes for tested versions and device measurements.

## Full-song Music × Lyrics correlation

The live Music Analysis workspace can build one full-duration correlation from the saved `music-analysis.json` and the current revision of `edit-timeline.json`. It reads canonical subtitle cues with `getSubtitleCues()`, which converts the frame-based clip start plus relative karaoke word offsets into absolute Timeline seconds. The selected report must belong to the same project. If the Timeline has a soundtrack clip, it must point at the same registered audio asset and its Timeline start establishes the audio origin. If there are subtitle cues but no soundtrack clip, the UI refuses to correlate until an explicit time origin is available; it does not silently assume the Timeline and audio start together.

`scripts/music-lyrics-map.ts` uses sorted temporal indexes and binary range lookup for points and intervals. `music-lyrics-map.json` retains cue/word IDs, exact timing, alignment state, beat/downbeat and section references, event IDs, event provenance references, local RMS summaries, pre-word cues, and composite event cues. It does not invent missing word boundaries or attach estimated alignment confidence. Untimed lyric text remains inspectable as untimed tokens. The compact `director-brief.json` links back to detail via `music-lyrics-map.json` and contains only measured section/energy/event/beat context; neither file adds emotional or creative interpretation.

The full map and Director Brief are saved separately from the original audio and lyrics data. They record the audio report fingerprint and a lyrics-only fingerprint derived from stable cue/word IDs, text, times, routing and the soundtrack origin. Visual-only Timeline edits do not invalidate lyric correlation. When Timeline Save changes the lyric fingerprint, FloxBow rebuilds the derived map, brief and vocal phrasing analysis from the existing audio report as part of that save. The phrasing analysis uses the saved audio-only RMS/F0 series; All-In-One-Infer, Demucs and acoustic extraction are not rerun. If automatic refresh cannot run, Timeline save still succeeds and reports the derived artifact as stale.

Music Analysis uses the shared Video Editor player for Play/Pause, seeking, event audition and lyric synchronization. On report load, the host maps the saved audio fingerprint (file size and modification time) to the current Media Library ID; re-linking an unchanged file therefore does not disable playback just because its ID changed. If the selected report source is not the Timeline soundtrack, **Use as Timeline soundtrack** connects it to the existing Timeline session. Save that Timeline change in the Video Editor to persist it.

Music × Lyrics follows the supplied standalone `index.html` layout and visual language: a compact audio summary, a lyric alignment panel with the white karaoke preview on the left and the seekable lyric list on the right. The lyric toolbar keeps the same rows and height when switching views: tabs and display options stay above shared Play/Pause and seek controls, while the white preview stage keeps a fixed height. The lyric list fills the height of the left editing column, and Auto follow keeps the current lyric as the third visible row. The word timing cards use restrained monochrome states: sung words are near-black, upcoming words are slightly lighter, and the selected/current word keeps the orange accent. Word timing cards remain on the nearest lyric through gaps: the previous lyric stays selected until the midpoint between its end and the next lyric's start, then the next lyric's cards take over. Whole-lyric shift and reset always target that same selected lyric. The white lyric stage has two views: **Karaoke preview** shows the active line; **Timed word layout** places every timed word on the shared Timeline time scale. Each word's width represents its start/end interval and its text stretches horizontally to fit while keeping a readable font height. Sung words are black, the active word orange, and upcoming words gray. During playback, the word layout follows frame updates from the Video Editor's shared Remotion player; it does not create an audio element or independent playback clock. The playhead remains centered and the words move beneath it; at time zero, the left half is empty. **Display settings** can remove word backgrounds/borders or hide the time ruler/playhead; **Clean text only** applies both settings. The bottom shared transport controls playback, volume, and Timeline seeking across workspace tabs; Music Analysis event and lyric controls use that same playhead and can seek or audition events through it. **Full analysis** opens the former dock and detail panels in a modal. Closing it unmounts those panels and their per-playhead filtering/rendering; the saved report and correlation remain available to reopen. The modal retains musical structure, waveform, energy, beat/downbeat navigation, event category controls, nearby events and provenance. **Hide event lanes** collapses drums, bass, vocals, other and mix/change tracks, skips their per-playhead filtering/rendering, and leaves the structural and waveform lanes. Clicking a word seeks to its exact start. Word timing controls sit below the white preview in spaced cards; their panel keeps a fixed height. Clicking an event seeks to it and plays a short window through the shared Timeline player. Word-boundary and whole-line timing controls create an in-memory draft first. **Save timing to Timeline** writes through the existing revision-checked Timeline API, which refreshes the derived correlation; **Reset this lyric** restores the last saved Timeline version. The Timeline remains the source of truth for caption playback.

## Vocal phrasing and kinetic direction

The **Kinetic direction** tab is a text-only project-ratio preview over the existing saved correlation. It shares the Music Analysis audio player and playhead; it does not create a second soundtrack, edit subtitle timing, or add clips to the Timeline. It compares three deterministic grouping strategies on the same cue/word IDs: `stretch` (the supplied sustain-threshold formula), `phrase-optimization` (duration, pause, punctuation and local musical context), and `hybrid` (optimization plus sustain candidates). The comparison cards show the active phrase at the shared playhead and summary metrics.

The browser-safe `@motion/lyrics-sync/phrasing` export exposes feature extraction and phrase planning without depending on React, Electron or the Timeline UI. Its versioned settings cover sustain ratio and duration, syllable/normal-word baselines, pause split and boundary strength, target group duration and word count, maximum words, music/event/energy weights, punctuation influence and boundary strength, and short-group threshold and penalty. The settings panel exposes core controls and advanced controls, recalculates the preview locally, and **Reset to factory defaults** restores `FACTORY_PHRASING_SETTINGS`. A saved plan stores the chosen algorithm/settings and its source revisions separately in `visual-phrase-plan.json`; `vocal-phrasing-analysis.json` schema v2 stores cue/word-linked features and per-verse estimated syllables/sec, acoustic articulation rate when available, pause duration/count, performed-to-normal duration ratio, a separately named word-duration variability index, and each word's relative duration compared with its verse. It retains review status, audio method/version provenance, and hashes for the music-report and lyrics revisions. The audio-only RMS/F0 series are stored once in `music-analysis.json` and returned alongside the derived artifact by the vocal-phrasing API. Syllable counts remain spelling estimates, not measured syllable boundaries; the variability index is not nPVI. Saving these artifacts does not modify `edit-timeline.json`.

The local `/api/media/<project-id>/music-analysis` GET returns the persisted report including `vocalProfile`. `/api/media/<project-id>/vocal-phrasing` GET returns `analysis` (verse/word prosody), `plan`, the same persisted `vocalProfile` series and a `stale` flag; POST recalculates from the saved Timeline and report without rerunning audio inference. Refreshing the full Music × Lyrics map also regenerates vocal phrasing. Every saved Timeline lyric/timing change rebuilds the map and prosody artifact from the cached report.

Phrase groups have stable IDs derived from their lyric cue and member word IDs, explicit grouping reasons and timing-quality labels. Syllable count is a rough spelling heuristic; long duration only creates a sustain candidate and does not identify an elongated vowel or establish emotion. Candidates inherit source quality from the saved cue and are not treated as verified when timing is estimated. The current module does not schedule entrance/exit animation or publish text clips to the Video Editor. The Timeline remains the eventual playback source of truth; publishing motion is a separate follow-up integration.
